과제 3장 항목(C1-1~C4-3)에 더해 목록에 없는 위험을 찾았다. 특히 **"누구나 접속 가능한 배포"와 "공개 저장소"라는 제출 조건 자체가 만드는 위험**(2장 D, 8장 G)을 따로 모았다. 이 표가 `CONSIDERATIONS.md`의 원본이 된다.

## 0. 읽는 법

- **판정**
  - [구현] 코드로 막고 테스트로 고정한다
  - [문서로만] 판단과 근거를 `CONSIDERATIONS.md`에 남기고 코드로는 다루지 않는다
  - [제외] 이 과제 범위에서 다루지 않는다. 이유를 적는다
  - **결정 필요** 사용자가 정할 것. 추천을 같이 적었다 (11장)
- **출처**: 과제 3장 항목 ID(C…), 1단계 숨은 요구(H…), 또는 **신규**(과제 목록에 없던 것)
- **ID**: D 공개 배포 · N 파일명·확장자 · U 업로드·저장 · P 정책 데이터 · X 화면·예외 · O 운영 · G 공개 저장소·기록 · V 개발·검증 과정
- 근거 문서는 12장에 링크를 모았다. 본문에는 [OWASP], [MS 이름 규칙], [MS 경로 정규화], [VirusTotal]로 줄여 적는다

## 2. 공개 배포가 만드는 위험 (D)

과제는 "면접 당일 누구나 접속 가능한" 배포를 요구하고 인증은 언급하지 않는다. 그러면 정책 관리 화면과 업로드 기능이 인터넷 전체에 열린다. 이 조건 하나에서 아래 위험이 나온다.

| ID | 위험·예외 (예) | 판정 | 근거·대응 | 출처 |
| --- | --- | --- | --- | --- |
| D1 | 누구나 정책을 바꾼다. 방문자가 고정 7개를 모두 해제하면 차단이 사라진다 | [구현] 공개 유지 + "기본값으로 초기화"(고정 전부 해제·커스텀 전부 삭제) + 변경 이력 표시(P7) — 문답 #10 | [OWASP]는 업로드를 인증된 사용자로 제한하라고 하지만, 과제는 "누구나 접속"을 요구하고 비밀번호는 공개 저장소에 둘 수 없다. 숨기는 대신 "누가 언제 바꿨는지 보이게, 되돌릴 수 있게"로 대응한다 | H1 |

| D3 | 200개 한도 소진. 누가 쓰레기 항목 200개를 채우면 아무도 추가하지 못해 면접 당일 "추가"를 시연할 수 없다 | [구현] D1의 초기화 + D6 요청 제한 | 필수 요구의 한도(R-A7)가 공개 환경에서는 서비스 거부 수단이 된다 | 신규 |
| D4 | 저장 공간 소진. 반복 업로드로 무료 저장 용량이 차면 면접 당일 업로드가 실패한다 | [구현] 파일 크기 상한(U2) + 보관 기한 삭제(U9) + 전체 사용량 상한에 닿으면 업로드 거부 | 상한값은 3단계에서 저장소 무료 한도를 확인하고 정한다 | 신규 |
| D5 | 악성 파일 배포 통로. 누가 올린 악성 파일이 우리 도메인 링크로 퍼진다 | [구현] 비공개 저장, 다운로드 없음 (문답 #6) | [OWASP]는 공개 조회를 제공하면 불법 콘텐츠 신고 수단을 두라고 한다. 조회 자체를 없애 그 필요를 없앤다 | H3 |
| D6 | 요청 폭주로 무료 한도를 넘겨 서비스가 정지되거나 느려진다 (함수 호출 수, DB 연산 시간) | [구현] 쓰기 요청(정책 변경·업로드)에 요청 제한. 저장 방식은 3단계 | 공개 엔드포인트는 남용을 가정한다 | 신규 |
| D7 | 검색 노출과 봇. 크롤러가 업로드 폼을 찾아 자동 제출한다 | [구현] `noindex` 메타 + `robots.txt` Disallow. 자동 제출은 D6이 받친다 | 비용이 거의 없다. CAPTCHA는 면접관 사용성을 해쳐서 넣지 않는다 | 신규 |
| D8 | CSRF. 다른 사이트가 방문자 브라우저를 시켜 정책 변경 요청을 보낸다 | [제외] — D1에서 인증을 넣으면 [구현]으로 바뀐다 (SameSite 쿠키 + Origin 검사) | [OWASP]는 업로드 CSRF 보호를 권하지만, 그 전제는 인증된 세션이다. 세션이 없으면 공격자가 직접 요청하는 것과 차이가 없다 | 신규 |
| D9 | 클릭재킹. 정책 화면을 보이지 않는 iframe에 넣고 클릭을 유도한다 | [구현] `Content-Security-Policy: frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy` | D8과 같은 이유로 실익은 작지만 비용이 더 작다(설정 몇 줄) | 신규 |
| D10 | 면접 당일 접속 불가. 잠들기·일시 중지·만료·첫 요청 지연 | [구현] 3단계의 선택 기준. DB 왕복을 포함한 상태 확인 경로 + 매일 자동 호출(예약 실행)로 장애를 먼저 안다 | 문답 #7: 1달 이상 방치해도 버텨야 한다 | H2 |
| D11 | 결제 수단을 연결한 플랜에서 초과 사용이 과금된다 | [구현] 결제 수단 없는 무료 플랜만 쓴다. 한도 초과 시 정지인지 과금인지 3단계에서 공식 문서로 확인한다 | 공개 배포 + 남용(D6)이 겹치면 비용 문제가 된다 | 신규 |
| D12 | 방문자 개인정보. 요청 제한·로그를 위해 IP를 저장한다 | [구현] 원본 IP는 저장하지 않는다. 요청 제한 키는 주기적으로 바뀌는 비밀값을 섞은 해시로 만들고 짧게 보관한다 | IP도 다른 정보와 결합하면 개인을 알아볼 수 있다. 목적(요청 제한)에 필요한 만큼만 남긴다 | 신규 |
| D13 | 업로드 결과가 다른 방문자에게 보인다. 파일명에 개인정보가 들어 있을 수 있다(예: `홍길동_등본.pdf`) | [구현] 이 브라우저에서 올린 것만 보여 준다(익명 방문자 ID 기준, D15). 전체 목록 API는 두지 않는다 — 문답 #12 | 비공개 저장(D5)을 해도 파일명 목록이 공개되면 정보가 샌다 | 신규 |
| D14 | 공개 데모 상태가 지저분하다. 면접관이 열었을 때 이전 방문자의 정책·업로드가 남아 있다 | [구현] 정책은 "기본값으로 초기화"(D1), 업로드 목록은 처음부터 내 것만 보임(D13) | 면접관의 첫인상이 "과제 초기 상태"와 달라진다 | 신규 |
| D15 | 익명 방문자 ID 쿠키. D13(내 업로드만)과 P7(나 / 다른 방문자)을 위해 브라우저를 구분해야 한다 | [구현] 서버가 만든 무작위 ID를 `HttpOnly`·`Secure`·`SameSite=Lax` 쿠키로 둔다. 개인정보를 담지 않고 추적·분석에 쓰지 않는다. 쿠키를 지우면 새 방문자가 된다 | 원본 IP(D12) 대신 쓸 수 있는 가장 약한 식별자. 인증이 아니므로 권한 판단에 쓰지 않는다 | 신규 |

## 3. 파일명·확장자 판정 (N)

판정 규칙은 1단계에서 확정했다(문답 #1~#4). 여기서는 그 규칙을 뚫거나 오판하게 만드는 입력을 모았다. [구현] 항목의 예시는 그대로 단위 테스트 케이스가 된다.

| ID | 위험·예외 (예) | 판정 | 근거·대응 | 출처 |
| --- | --- | --- | --- | --- |
| N1 | 대소문자: `file.PDF`, `setup.EXE` | [구현] NFKC 뒤 소문자로 비교 | [MS 이름 규칙]: Windows는 이름의 대소문자를 구분하지 않는다고 가정하라 | C1-2 |
| N2 | 이중 확장자: `file.exe.txt`는 `txt`로 통과, `photo.jpg.exe`는 `exe`로 차단 | [구현] 마지막 확장자 (문답 #1) | 점 뒤 전부 검사하면 `naver.com.png`를 고정 `com`이 막는다. [OWASP]의 이중 확장자 경고(`.jpg.php`)는 끝에 고정되지 않은 검사(`\.jpg`)가 뚫리는 경우라, 마지막 확장자만 보는 이 방식에는 해당하지 않는다 | C1-2 |
| N3 | 복합 확장자: `a.tar.gz`, `atar.gz`, `pkg.tar.zst` | [구현] 점 경계 2단 정확히 일치. `a.tar.gz` 차단, `atar.gz` 통과, 3단 항목은 입력 거부 (문답 #4) | AI 오류 E1 | C1-2 |
| N4 | 점으로 시작: `.env`→`env`, `.exe`→`exe`, `.htaccess`→`htaccess` | [구현] 마지막 점 뒤 (문답 #2) | Node `path.extname('.exe')`는 `""`(1단계 실측). [MS 이름 규칙]도 점으로 시작하는 이름(`.temp`)을 허용한다 | C1-3 |
| N5 | 확장자 없음: `Makefile`, 셔뱅(`#!`) 스크립트, ELF 실행 파일 | [구현] 통과시킨다 + [문서로만] 확장자 없는 실행 파일의 위험 | 차단 목록 방식에서는 "확장자 없음"을 막을 근거가 없다. 비공개 저장이라 실행될 경로가 없다 | C1-3 |
| N6 | 끝 점·공백: `evil.exe.`, `evil.exe ` | [구현] 판정 전에 끝의 점·공백을 지운다 | [MS 경로 정규화] "trailing periods and spaces (U+0020) are removed" — Windows에서는 실제로 `evil.exe`가 된다. `extname` 실측은 `"."`, `".exe "` | 신규 |
| N7 | 전각·호환 문자: `ｅｖｉｌ.ｅｘｅ` | [구현] NFKC 정규화 | Windows가 전각 `ｅｘｅ`를 실행 파일로 보지는 않는다. 그래도 차단 목록에서는 오탐이 미탐보다 싸므로 보수적으로 막는다 | C1-4 |
| N8 | 제어·방향 문자: RLO(U+202E)를 넣은 `invoice‮fdp.exe`는 화면에 `invoiceexe.pdf`로 보인다. 널 바이트 `evil.exe\0.jpg`, 제로폭 문자 | [구현] 파일명에 C0/C1 제어 문자, 양방향 제어 문자(U+202A~202E, U+2066~2069), 제로폭 문자(U+200B~200D, U+FEFF)가 있으면 사유와 함께 거부 | RLO 예는 마지막 확장자 규칙으로 원래 막힌다. 하지만 거부 메시지·목록에 그 이름을 그대로 보여 주면 사용자를 속인다. 널 바이트는 C 기반 저장 계층에서 이름을 잘라 `.exe`로 만든다([OWASP]). | N9 | macOS 한글 파일명: `한글.txt`가 자모가 분리된 NFD로 온다 | [구현] 표시·저장용 이름은 NFC로 정규화 (판정용은 N7의 NFKC) | 같은 이름이 두 형태로 저장·표시되는 것을 막는다. NFKC는 전각 문자 모양까지 바꾸므로 표시용으로는 NFC를 쓴다 | 신규 |
| N10 | 매우 긴 파일명 | [구현] UTF-8 255바이트 초과 거부 (1단계 D12) | 대부분 파일 시스템의 이름 길이 한도. 한글은 85자 정도 | C1-3 |
| N11 | 경로가 섞인 이름: `../../a.exe`, `..\evil.exe`, `C:\fakepath\a.exe` | [구현] `/`·`\` 뒤 마지막 부분만 이름으로 본다. 저장 경로에는 원래 이름을 쓰지 않는다(U4) | 브라우저는 보통 이름만 보내지만 직접 요청은 무엇이든 보낼 수 있다 | C1-7 |
| N12 | NTFS 대체 데이터 스트림·IIS 세미콜론: `evil.exe::$DATA`, `evil.asp;.jpg` | [구현] 이름에 Windows 금지 문자(`< > : " \| ? *`)가 있으면 거부 | `evil.exe::$DATA`는 마지막 점 뒤가 `exe::$data`라 이름 판정을 통과하지만 NTFS에 쓰면 `evil.exe`가 된다. 원래 이름으로 저장하지 않아 실해는 없지만, [OWASP]가 콜론이 든 이름을 거부하라고 하고 정상 파일명에는 드물다 | 신규 |

| N14 | 빈 이름, 이름 없는 파일 필드, `.`·`..` | [구현] 거부. 끝 점을 지운 뒤 빈 문자열이 되는 경우 포함 | 표시할 이름도 판정할 확장자도 없다 | 신규 |

| O6 | 백업·복구 | [제외] | 데모 데이터라 잃어도 영향이 작다. 무료 플랜의 복구 기능은 3단계에서 참고로만 본다 | 신규 |

## 8. 공개 저장소·기록 (G)

저장소를 public으로 두기로 했다(문답 #8). 코드뿐 아니라 설계 문서·PROMPT_LOG·대화 원문이 함께 공개된다.

| ID | 위험·예외 (예) | 판정 | 근거·대응 | 출처 |
| --- | --- | --- | --- | --- |
| G1 | 비밀값 커밋: DB 접속 문자열 | [구현] `.env*` 무시 + `.env.example`에는 키 이름만. 하네스 blockSecretAccess, push 전 접속 문자열 검색 | 공개 저장소에서는 커밋 히스토리째 노출되고 되돌릴 수 없다 | 신규 |
| G2 | 기록에 개인·다른 회사 정보가 들어간다 (PROMPT_LOG, 설계 문서, 커밋) | [구현] push 전 민감 단어 검색 (팀 규칙) | AI가 작업 중 읽은 자료가 기록에 섞일 수 있다 | 신규 |
| G3 | 대화 원문 첨부: 로컬 경로(사용자 이름), 다른 작업 내용, 붙여 넣은 자료 | [구현] 추출 스크립트에 홈 경로 치환과 제외 목록. 첨부 전에 사용자가 확인한다 | 과제 4-1이 원문 기록을 권한다 | 신규 |
| G4 | 과제와 풀이가 공개돼 다른 지원자가 참고한다 | [제외] | 막을 수 없다. 공개를 정할 때(문답 #8) 감수했다 | 신규 |
| G5 | 판정 로직이 공개돼 우회 방법을 연구할 수 있다 | [제외] | 보안을 코드 비공개에 기대지 않는다(케르크호프스 원칙). 실제 방어는 저장 구조(비공개, 무작위 키, 실행하지 않음)다 | 신규 |

## 9. 개발·검증 과정 (V)

과제의 절반이 "AI를 어떻게 썼는가"라서, AI와 함께 만드는 과정 자체의 위험도 적는다.

| ID | 위험·예외 (예) | 판정 | 근거·대응 | 출처 |
| --- | --- | --- | --- | --- |
| V1 | 같은 AI가 쓴 구현과 테스트가 같은 오해를 공유한다. 테스트가 통과해도 규칙 자체가 틀렸을 수 있다 | [구현] 테스트 케이스를 외부 근거에서 먼저 뽑는다(1단계 실측표, [MS 이름 규칙], [MS 경로 정규화], [OWASP] 우회 목록) → TDD red. 위험 목록은 Codex 교차 검토, PR은 사용자 리뷰 | | 신규 |

| V4 | 표준 파싱 함수의 기본 동작을 믿는다 (`path.extname`) | [구현] 1단계 실측표를 그대로 테스트로 쓴다 | | 신규 |
