## 1. 개요

확장자 정책을 DB에 저장하고, 정책·이력 API 6개와 정책 관리 화면을 만들었습니다(설계 11장 순서 3). 구현 전에 진행 방식과 코드 구성을 먼저 확인받았습니다.

## 4. 확인하며 고친 것

- 서버 오류 로그의 원인이 비어 있었습니다. DB를 멈춰 보니 연결 거부 오류(AggregateError)는 message가 빈 문자열이라 로그에 요청 번호만 남았습니다. message가 비면 오류 코드(`ECONNREFUSED`)·이름을 남기게 고치고 테스트를 더했습니다.
- `next dev`를 실행하자 Next.js가 저장소의 `AGENTS.md`(하네스 규칙)에 자체 안내 블록을 덧붙였습니다. 의도한 변경이 아니라 되돌렸고, 점검표 "push 전"에 도구가 만든 변경을 `git status`로 확인하는 항목을 더했습니다. 확인을 받아 `next.config.ts`에 `agentRules: false`를 넣었고, 개발 서버를 다시 켰을 때 `AGENTS.md`가 바뀌지 않는 것을 확인했습니다.
- 첫 요청은 개발 서버가 라우트를 컴파일하느라 2초 넘게 걸렸고, 그동안 화면 버튼이 막혀 있었습니다. 개발 모드에서만 생기는 지연입니다.

## 5. 리뷰 반영

별도 세션에서 저와 Claude가 PR을 검토한 뒤 같은 브랜치에 반영했습니다. 커밋은 PR 본문의 "리뷰 반영" 절에 있습니다.

- 방문자 쿠키를 뺀 뒤 남은 "누가" 문장을 정리했습니다(위험 D1·D2·P7, 설계 2.2). 이력은 언제·무엇을·어떻게 바꿨는지만 남기고 누가는 기록하지 않습니다. 인증·쿠키·IP가 모두 없어서이고 우리 결정입니다. 운영이라면 관리자 계정 ID를 남깁니다. 과제 3-2의 답은 제출 PR의 CONSIDERATIONS.md에 분명히 적습니다. 쿠키에 기대던 다른 행도 훑었고 D16은 이미 맞춰져 있었습니다(AI 오류 E16).
- 요청 번호를 잇습니다: 모든 정책 API 응답에 `X-Request-Id`, 오류 본문에 `requestId`, 화면은 서버 오류(5xx)일 때만 오류 문구 뒤에 `(오류 번호 f7d5c5e8)`처럼 짧게 보여 줍니다. 정책을 바꿀 때마다 커밋 뒤 서버 로그 한 줄(`{"event":"policy_change","requestId","action","ext"}`)을 남기고, 이력 행에도 같은 번호가 있습니다. 로그에 IP나 다른 개인 정보는 남기지 않습니다.
- 1KB 본문 제한: `Content-Length`가 1KB를 넘으면 본문을 읽지 않고 413 `BODY_TOO_LARGE`. 헤더가 없거나 틀린 경우를 위해 읽은 뒤 검사도 남겼습니다. 주석은 실제 동작대로 고쳤습니다(AI 오류 E17).
- 테스트를 먼저 썼을 때 새 테스트 8개가 실패했고, 구현 뒤 201개 통과합니다. 로컬 개발 서버에서 DB를 멈추고 체크박스를 누르면 화면에 `(오류 번호 f7d5c5e8)`가 보이고, 서버 로그의 `server_error` 줄에 같은 번호가 있는 것을 확인했습니다.

두 번째 리뷰(같은 방식으로 다시 검토, 세 가지 모두 반영 확인 뒤 추가 지적):

- AI 오류 노트 E16·E17의 "잡은 계기"를 "PR #8 리뷰 — 별도 세션의 Claude가 찾고 제가 반영을 정함"으로 고쳤습니다. 리뷰 세션에서 나온 지적은 앞으로도 이렇게 구분해 적습니다. PROMPT_LOG 4장(작업 방식을 바꾼 도구)에 독립된 리뷰 세션 한 줄을 넣었습니다.
- 화면의 오류 번호는 서버 오류(5xx)일 때만 붙입니다. 중복·형식 오류처럼 방문자가 고칠 수 있는 오류에 번호가 붙으면 시스템 장애처럼 보이기 때문입니다. 응답 헤더와 본문의 `requestId`는 그대로입니다. 규칙은 `errorText`(순수 함수)로 빼서 테스트로 고정했습니다(먼저 6개 실패 → 207개 통과).
- `policy-repo.ts`의 `type Record`가 TypeScript 내장 `Record`를 가려 `AuditWriter`로 바꿨습니다.
