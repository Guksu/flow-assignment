## 1. 개요

설계 4장의 판정 규칙을 순수 함수로 만들었습니다(설계 11장 순서 2). 브라우저와 서버가 같은 함수를 쓰므로 Node 모듈 없이 문자열 처리만 합니다. 테스트 케이스를 뽑는 중에 안 보이는 글자로 확장자를 숨겨 화면을 속이는 경우를 찾아(Windows도 실행 파일로 보지 않아 실행 문제는 아님, 위험 N21), 규칙을 넓히고 이모지도 거부하기로 했습니다.

## 2. 작업 내용

| 파일 | 하는 일 |
|------|------|
| `upload-name.ts` | 업로드 파일 이름 → 화면용 이름(NFC), 단일·복합 확장자. 거부 코드 `NAME_EMPTY`·`NAME_EMOJI`·`NAME_CONTROL_CHAR`·`NAME_FORBIDDEN_CHAR`·`NAME_TOO_LONG` |
| `custom-extension.ts` | 커스텀 입력 정규화와 검사. 결과는 DB CHECK와 같은 형식 |
| `policy.ts` | 막을지 판단. 복합을 먼저 봐서 더 구체적인 규칙을 사유로 |
| `messages.ts` | 오류 코드 → 방문자 안내 문구(화면·API 공용) |

- 실패는 오류를 던지지 않고 `{ ok: false, code }` 같은 결과로 돌려줍니다(문답 #32).
- 안 보이는 글자는 유니코드 속성으로 정의했습니다: 제어(Cc)·서식(Cf) 문자, 줄·문단 구분자(Zl·Zp), Default_Ignorable_Code_Point. 손으로 나열한 목록에서 빠지는 글자가 없게 하기 위해서입니다(AI 오류 E15).
- 이모지는 기본이 이모지 모양인 글자(Emoji_Presentation), 이모지 모양 선택자(U+FE0F), 키캡(U+20E3)으로 판단합니다. ©·™·®처럼 기본이 글자 모양인 기호는 허용합니다.

## 3. 진행 과정

- 구현 전에 진행 방식과 코드 구성을 먼저 확인받았습니다. 첫 질문은 용어 위주라 다시 하라는 요청을 받고 쉬운 말로 다시 물었습니다.
- 테스트 케이스를 뽑으며 Node로 실측했습니다. 기존 규칙(제어 문자 + 양방향 서식 U+202A~E·U+2066~9)으로는 soft hyphen, zero width space, LRM, 한글 채움 문자 등을 확장자 안에 넣은 이름이 화면엔 `evil.exe`로 보이면서 통과했습니다. LRM·RLM·ALM은 양방향 서식인데 목록에서 빠져 있었습니다.
- 결정(문답 #31): 안 보이는 글자는 예외 없이 거부, 이모지도 거부, 닮은 글자(키릴 `е`)는 문서로만.
- "대부분 서비스처럼"을 공식 문서로 확인했습니다(서브에이전트 조사 뒤 Dropbox·Box·OneDrive·S3 원문을 다시 대조). Dropbox·S3는 이모지를 허용하고, Box는 BMP 문자만 받습니다. 결과를 보고도 거부를 유지했습니다(문답 #34, 설계 13장).

## 6. 리뷰 반영

별도 세션에서 저와 Claude가 PR을 검토한 뒤 같은 브랜치에 반영했습니다. 커밋은 PR 본문의 "리뷰 반영" 절에 있습니다.

- 이모지 거부 이유를 제 말로 인용하고, "사내 도구"는 과제 원문에 없는 가정이라고 밝혔습니다. 정상 파일도 막히는 비용(`🔥최종 기획안.pptx`, `✅ 확인완료.xlsx`)을 적었습니다(설계 문답 #34, 위험 N8)
- 하트 경계를 테스트로 고정했습니다: `❤사랑.jpg`는 통과, `❤️사랑.jpg`는 거부
- 이모지 거부 문구에 할 일을 붙였습니다
- PROMPT_LOG 장면의 "왜 물었나"를 실제 이유로 바꾸고, Claude가 대신 쓴 판단 문장에 초안 표시를 붙였습니다
- 안 보이는 글자 건을 "우회"가 아니라 화면 속임으로 표현을 맞췄습니다(위험 N21)
- 문답 #33의 인용 아래에 뜻을 푼 초안을 붙였습니다
- 점검 스크립트가 인용 안의 "사용자"를 세지 않게 했습니다. 인용은 원문 그대로라는 가이드 규칙에 맞추기 위해서입니다
- 리뷰 반영 뒤 테스트 129개 통과(하트 경계·비용 사례·문구 테스트 4개 추가)
- 문서 점검은 초안 표시 3곳(PROMPT_LOG 2곳, 설계 문답 #33 1곳) 때문에 실패 상태입니다. 제가 고친 뒤 통과시킵니다
