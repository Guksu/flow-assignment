# AI 작업 점검표

이 과제에서 AI(Claude)가 실제로 틀린 것을 패턴으로 묶어, 같은 실수를 다시 하지 않도록 작업 중에 확인하는 표입니다. 사례는 설계 문서의 [AI 오류 노트](design/2026-10-21-file-extension-policy.md#15-ai-오류-노트)(E…)와 위험 표 [13장 Codex 비교](analysis/02-risks.md#13-codex-교차-검토)(#…)를 가리킵니다.

## 언제 보나

| 시점 | 볼 패턴 |

| 추천안을 내거나 결정을 기록하기 전 | A1 출처 혼동 · A2 결정 간 영향 · A8 대응의 실효 · A9 과한 차단 · A10 한 가지 기준만 본 추천 · A11 구현 쪽으로 기우는 판정 |
| 제 의도·이유를 기록할 때 | A12 추정으로 채운 기록 |
| 판정 규칙을 정의하거나 구현하기 전 | A4 말로만 정의한 규칙 · A7 표준 함수 기본 동작 · A9 과한 차단 |
| 외부 근거를 인용할 때 | A3 기억·요약 인용 |
| "보장된다", "원자적이다", "항상" 같은 주장을 쓸 때 | A5 동작 가정 |

| 커밋·push 전 | 아래 "push 전" 절 |

## 패턴

| ID | 패턴 | 사례 | 점검 질문 | 하는 일 |
| --- | --- | --- | --- | --- |
| A1 | 출처 혼동 — 과제 원문의 요구, 제 결정, AI 추론을 섞어 씀 | E3, E5 | "과제가 요구한다"고 쓴 문장마다 원문 문장을 가리킬 수 있는가? | 근거에 출처를 붙임: 과제 원문(절) / 문답 #N(결정) / 추론. 원문에 없으면 "우리 결정"이라고 씀 |
| A2 | 결정 간 영향 누락 — 결정 하나가 다른 항목의 전제를 바꾸는데 다시 보지 않음. 함께 추천한 것끼리 서로 영향을 주는 것도 놓침 | E2, E7 | 이 결정에 기대는 항목이 무엇인가? 같은 라운드의 다른 추천과 충돌하거나 한쪽을 불필요하게 만들지 않는가? | 결정 표 근거 열에 관련 위험 ID를 적음. 결정을 바꾸면 그 ID들을 다시 훑고, 바뀐 판정을 기록함 |
| A3 | 기억·요약 인용 — 원문을 확인하지 않고 기억으로 인용하거나, 웹 요약 도구의 요약을 원문처럼 옮김 | E4, E8 | 인용한 문장을 원문에서 그대로 받아 봤는가? | 원문 문장을 그대로 받아 대조함. 요약 도구를 거쳤다면 원문 HTML에서 같은 문장을 검색해 확인함. 문서에는 요지와 링크·확인 날짜·확인 방법(원문 전체 / 원문 대조 / 요약 도구 결과)을 적고, 긴 원문은 옮기지 않음. 확인 전이면 "확인 전"이라고 씀 (3단계에서 다듬음) |
| A4 | 말로만 정의한 규칙 — 비교 단위·순서·경계가 빠진 규칙. 여러 단계 변환의 순서와 단계끼리의 상호작용을 따지지 않음. 한 곳에서 고친 순서 문제를 같은 성격의 다른 변환에 적용하지 않음 | E1, E9, E12 | 이 규칙을 입력 → 출력 예시로 적을 수 있는가? 각 단계가 다음 단계의 입력을 새로 만들지 않는가(예: NFKC가 점을 만든다)? | 규칙은 입력 → 출력 표와 반례로 적고, 그 표를 그대로 테스트 케이스로 씀 |
| A5 | 동작 가정 — DB 동시성, 플랫폼 제한, 라이브러리·DB 기능을 확인 없이 "보장된다" / "못 한다"고 씀 | E6, E10 | 이 보장의 근거가 공식 문서나 실행 결과인가? | 공식 문서 링크를 달거나, 동시 요청 같은 실행 테스트로 확인함 |
| A6 | 손으로 센 숫자 — 요약 표의 수치를 어림으로 적음 | 2단계 요약 표 (PROMPT_LOG P3) | 이 숫자를 낸 명령이 있는가? | 수치는 스크립트로 세고, 기록에 명령을 남김 |
| A7 | 표준 함수 기본 동작을 믿음 — 판정에 쓰는 표준 함수가 경계 입력에서 다르게 동작함 | 1단계 실측 (`path.extname('.exe') === ''`) — 미리 잡은 사례 | 판정에 쓰는 표준 함수를 경계 입력으로 돌려 봤는가? | 경계 입력 실측표를 만들어 테스트로 고정함 |
| A8 | 대응의 실효 — 다른 위험의 대응을 끌어다 이 위험의 대응이라고 적음 | 위험 D1 (#8: "초기화"는 차단을 푸는 동작이라 차단 해제 위험의 대응이 아님) | 이 대응이 이 위험의 발생 가능성이나 피해를 실제로 줄이는가? | 줄이지 못하면 위험을 "수용"으로 판정하고 그렇게 씀 |
| A9 | 과한 차단 — 거부 규칙을 넓게 잡아 정상 입력까지 막음 | 위험 N8 (#10: 제로폭 문자 전체 거부가 `👩‍💻.txt`를 막음), N10 (#16: 바이트 상한이 긴 한글 이름을 막음) | 이 거부 규칙에 걸리는 정상 입력을 하나라도 찾아봤는가? | 거부 규칙마다 정상 반례를 테스트에 넣음 |
| A10 | 한 가지 기준만 본 추천 — 효과나 구현 편의 한 축으로 추천하고, 정책·법적 적절성, 확장성, 실무 관행 같은 다른 축은 제가 묻기 전에 보지 않음 | E2, E11 | 이 추천을 다른 기준(확장성, 운영, 법·정책, 다른 서비스는 어떻게 하나)으로 보면 결론이 바뀌는가? | 추천마다 최소 두 축으로 비교하고, 다른 서비스 사례가 필요하면 공식 문서로 확인함 |
| A11 | 구현 쪽으로 기우는 판정 — 찾은 위험마다 [구현]을 붙여 범위가 과제 요구보다 커짐 | E13 | 이 항목을 마감 안에 확실히 동작시키고, 제가 면접에서 설명할 수 있는가? 필수 요구(R)·판정 규칙 핵심인가? | 아니면 [문서로만]으로 두고 "왜 안 했나 / 실제라면"을 남김. 판정 수를 스크립트로 세어 비율을 봄 |
| A12 | 추정으로 채운 기록 — 제 의도·이유를 AI가 짐작해 쓰거나 "추천 근거에 동의"로 채움 | E14 | 이 문장이 제가 실제로 한 말인가? | 제 입력은 그대로 인용함. 의도·이유를 모르면 묻거나 비워 둠. 추천대로 골랐어도 어느 근거가 컸는지 물음 |

## push 전

- 공개 저장소입니다. 다른 회사·개인 정보, 비밀값, 접속 문자열이 커밋에 없는지 검색합니다 (`docs/harness-rules.md`)
- 문서에 실제 제어 문자(예: U+202E)를 넣지 않습니다. 코드 포인트로 표기합니다 (위험 N8 사례가 문서에서 재현된 적이 있습니다)
- 커밋 메시지는 `-m`으로 씁니다(`blockAttribution: true`라 `commit -F`는 하네스가 막습니다)

## 검증에 효과가 있었던 방법

| 방법 | 잡은 것 |
| --- | --- |
| 실행해서 재현 (Node 한 줄, Docker Postgres) | 표준 함수 우회(1단계), 정규화 순서 우회(E9·E12), 200개 동시 추가 201개(E6 재현)와 잠금 효과 |
| 원문 문장 대조 | OWASP 오인용(E4, E8) |
| 스크립트로 세기 | 요약 표 수치 오류 |
| 다른 모델 교차 검토 — 독립 작성 → 초안 대조 두 번 | 지적 20건, 그중 같은 종류의 실수가 반복된다는 것(E5·E7·E8) |
| 제 짧은 반문 | 느슨한 규칙(E1), 놓친 관점(E2), 원문 대조 계기(E3) |

## 이 문서 관리

- AI 오류 노트에 새 항목을 적으면, 이 표의 패턴에 사례를 붙이거나 새 패턴을 만듭니다
- 패턴이 늘어도 한 화면 안에 둡니다. 사례는 ID로만 가리키고 설명은 오류 노트에 둡니다
